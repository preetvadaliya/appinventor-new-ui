Client restructure: today and proposed

Every client file on MIT's master, mapped to where it goes when logic, shared screens and each layout's look are separated. Pick a file on either side to see where it comes from or goes to, and why.

Four folders, one direction

layouts/
Each layout is self-contained: its own controls (buttons, menus, dialogs), its own frame (top bar, toolbars, project list), its menu arrangement, tokens for light and dark, and icons. Adding a layout means adding one folder.
classic/
neo/
nova/
↓ may import the folders below, never a sibling layout
features/
Written once, looks like whichever layout is active: designer, the user's app components (Mock*), properties, blocks, assets and every dialog. They use control interfaces, never a concrete layout class.
↓
controls/
The contract: interfaces for Button, MenuButton, Dialog, TextField …, the keyboard, focus and ARIA behaviour they share, and a plain standard controls a new layout can start from.
↓
core/
Logic with no widgets and no CSS: actions, presenters, project and settings models, RPC, the theme service. Testable without a browser.

Example: the New Project button

The action is defined once. Each layout only decides where its button goes and how it looks. On master today, neo places New project in the toolbar's left group and Move, Export and Gallery in the centre; nova could move it to the right without touching any logic.

Proposed

Rules a build check enforces

  1. core imports no GWT widgets and nothing from controls, features or layouts.
  2. features import control interfaces only, never ClassicButton or NeoDialog.
  3. layouts/x never imports layouts/y. A new layout extends controls/standard, never another layout.
  4. Only the active layout's CSS is loaded: its tokens.css, controls.css and views.css, plus the shared base.css. Switching light/dark flips data-theme on <html>; no reload.
  5. Menus name actions by id. Enabling, hiding or relabelling happens on the action, never by widget name.
