## Summary
One umbrella issue on `mit-cml/appinventor-sources` describes the restructuring, links
this tracking repository, and asks MIT reviewers to raise objections before P1 starts.
Every later PR links back to it. No code changes.

## Why
About 40 PRs will land over several months, each small and each claiming "no visual
change". Reviewers who meet them one at a time cannot see where they lead, and the late
package moves (P7-38, P7-39) touch almost every client file. Objections are cheap before
P1-03 and expensive after P4.

## Read first
- `docs/00-overview.md`
- `docs/09-migration.md`
- `docs/10-pr-rules.md`

## In scope
- Make this tracking repository public (or confirm it is) and note its URL
- Open the umbrella issue upstream with the text below
- Pin the issue link in this repo's `README.md`

## Out of scope
- The package-move window (C-02); nova (C-03)
- Any code or PR

## Steps
1. Fill in the two placeholders and open the issue titled
   `New UI: classic and neo as independent layouts (umbrella)`.
2. Ask in the issue for named reviewers and for objections within two weeks.
3. Post the link in the MIT developer channel the team already uses.
4. Record answers as comments in this repo; turn agreed changes into ticket edits.

Issue text:

> **Goal.** Make classic and neo self-contained layouts on top of shared logic, so that
> neo no longer subclasses classic, menus and toolbars stop finding buttons by name,
> and light/dark switches without a page reload. Neo stays the default layout.
>
> **Plan.** Tracking repo with design docs, decisions and every ticket:
> `<TRACKING_REPO_URL>`. Phases: P0 groundwork and a screenshot diff script; P1 layouts
> chosen by id; P2 live light/dark; P3 actions with ids; P4 independent views; P5 one controls
> of buttons, menus, dialogs and inputs per layout; P6 per-layout CSS, `Ya.css` removed;
> P7 final package moves and a test for the import rules.
>
> **How PRs look.** One ticket, one PR, titled `[new-ui <KEY>] …`, linking this issue.
> At most ~400 added lines and ~20 files; pure `git mv` PRs are larger but contain no
> edits. No visual change except P2's live light/dark switch; every PR attaches a
> before/after screenshot diff of 8 screens × classic/neo × light/dark. Old and new code
> coexist inside a phase; the phase's last PR removes the old path.
>
> **What we ask.** Objections to the target structure or the order before P1 starts
> (`<DATE>`), and one or two reviewers. The package moves (P7) will be scheduled with you
> so open PRs can be rebased the same day.
