## Summary
Classic and neo each get their own `Dialog`, `Wizard`, `TextField`, `Select`, `Checkbox`
and `Tree` in `layouts/<layout>/controls/`, returned by `ClassicControls` and `NeoControls`. They produce
the same markup and class names as today, so the shared dialogs and editors that move to
the controls next (P5-28 to P5-32) look exactly as they do now. Users see no change.

## Why
- Dialogs and inputs have no layout-specific Java today; the two looks differ only
  through CSS. Neo restyles dialogs with `.ode-DialogBox …` rules
  (`style/neo/neo.css:1412-1501` and 1167-1196 inside a media query) and trees with
  `.gwt-Tree …` (`neo.css:601-625`, 1073). Classic gets the same selectors from
  `style/classic/variableColors.css` and `war/static/css/Ya.css`.
- The only neo-specific dialog class, `style/neo/NewYoungAndroidProjectWizardNeo.java`, is
  never instantiated (`UiStyleFactory.createNewYoungAndroidProjectWizard()` has no
  caller), so neo has never had a dialog of its own.
- P6-36 needs one class per layout and piece to hang that layout's `controls.css` rules on.

## Out of scope
- `Radio` and `Collapsible`: both layouts keep `StandardControls`'s pieces until one needs its
  own
- Moving any CSS (P6-36); converting dialogs and editors to the controls (P5-28 to P5-32)
- Visual changes to either layout's dialogs

## Steps
1. Each class extends its `controls/standard` counterpart (`ClassicDialog extends
   StandardDialog`, `NeoTree extends StandardTree` …). No class extends or imports
   another layout's class.
2. Keep the DOM and class names exactly as the standard piece renders them
   (`ode-DialogBox`, `Caption`, `dialogContent`, `gwt-Tree`, `gwt-ListBox`,
   `gwt-CheckBox`, `gwt-TextBox`). The value of this ticket is the seam, not new markup.
3. `ClassicWizard` and `NeoWizard` keep the button order Cancel, Back, Next, OK
   (`wizards/Wizard.java:139-142`) and the frame classes `ode-DialogBox` (line 87),
   `ode-WizardPage`, `ode-WizardContent` and `ode-DialogButtons` (lines 137-154).
4. Override in `ClassicControls` and `NeoControls`: `dialog()`, `wizard(…)`, `textField()`,
   `select()`, `checkbox()`, `tree()`.
5. Add a test that both layouts' controls return their own class for each of the six factories
   (plain JUnit if the factories can run outside GWT; otherwise a `GWTTestCase` next to
   `appengine/tests/com/google/appinventor/client/OdeTest.java`).

## Acceptance criteria
- [ ] Twelve new classes, six per layout; each extends a `controls/standard` class only.
- [ ] `layouts/classic/**` imports nothing from `layouts/neo/**` and the reverse.
- [ ] With `UiLayout=CLASSIC`, `Controls.active().dialog()` is a `ClassicDialog`; with `NEO`, a
      `NeoDialog` (same for the other five pieces).
- [ ] Rendered DOM of a dialog with a text field, a select, a checkbox and a tree is
      identical to the `StandardControls` rendering in both layouts.
- [ ] Snapshot diff shows no change in classic or neo, light or dark.

## Rules
- At most ~400 added lines and ~20 files.
- No visual change.
- A layout never imports or extends another layout.
- Short conventional commit subjects, e.g. `refactor(controls): classic and neo dialogs`;
  no AI attribution.
