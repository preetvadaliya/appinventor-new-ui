## Summary
Adds the action framework: an `ActionId` enum, an abstract `Action` (label, `IconKey`,
enabled, visible, change listeners, `run()`), an `ActionRegistry` and a binding helper.
Toolbar items, menu items and buttons accept `action="…"` next to today's `Command`
children. No toolbar or menu moves to it yet, so users see no change.

## Why
A menu entry today is a widget with a string name and a `Command` child, e.g.
`<ai:DropDownItem name="New" …><actions:NewProjectAction/></ai:DropDownItem>`
(`TopToolbar.ui.xml:25-27`). Every template makes its own `Command` instance, so nothing
holds the state of "New project". Code finds widgets by name or by translated caption:
`DropDownButton.setItemEnabled()` compares `item.getText()` with a caption
(`widgets/DropDownButton.java:405-414`); `Toolbar.setButtonEnabled()` reads a map keyed by
name (`widgets/Toolbar.java:172-177`). There are 60 `Command` classes (44 in `actions/`,
16 in `editor/youngandroid/actions/`) and 121 by-name calls.

How commands are attached today: `ToolbarItem`, `DropDownItem`, `TextButton`,
`DropDownButton` and `Toolbar` carry `@ElementParserToUse`. That annotation is not stock GWT;
it comes with the patched `UiBinderWriter` in `lib/gwt_svg/lib-gwt-svg-0.5.15.jar`, which
runs the annotated parser first and GWT's `BeanParser` after it (`getParsersForClass`).
`ToolbarItemParser` and `DropDownItemParser` consume the one child element and emit
`field.setCommand(child)`; `TextButtonParser` does so only when the type is exactly
`TextButton` (`TextButtonParser.java:20`). Attributes are left to `BeanParser`, which picks
`EnumAttributeParser` for an enum-typed setter. So `action="NEW_PROJECT"` works on these
elements without touching any parser, and both forms can sit in the same template.

## Steps
1. `Action`: abstract `run()`; `getId()`, `getLabel()`/`setLabel()`, `getIcon()`,
   `isEnabled()`/`setEnabled()`, `isVisible()`/`setVisible()`, `onChange(Runnable)`.
   Setters notify only on a real change. Plain Java, no GWT import (rule 1).
2. `ActionRegistry`: `register(Action)` (rejects a second action for an id), `get(ActionId)`
   (throws naming the id if missing), one shared instance.
3. `IconKey`: semantic keys (`ADD`, `IMPORT`, `FOLDER_NEW` …), one per Material Symbol the
   neo toolbar and menu templates use today (26 glyphs).
4. `setAction(ActionId)` on `ToolbarItem`, `DropDownItem` and `TextButton`. `ToolbarItem` and
   `DropDownItem` keep a reference to the widget built for them, so code can show, hide or
   enable that one placement by reference (also for items built in code).
5. `Toolbar.add(ToolbarItem)` and `DropDownButton.addItem(DropDownItem)`: with an action, the
   click calls `run()` and `ActionBinding` mirrors enabled (plus `aria-disabled`, as
   `setItemEnabledById` does), visible and label; without one, use the `Command` as today.
   A `ToolbarItem` with neither (the "Screens: " label, `DesignToolbarNeo.ui.xml:23`) gets no
   click handler. If both are set, the action wins.
6. `DropDownButton.setAction()` binds only visible and enabled; a click still opens the
   menu (the neo Export menu button is `EXPORT`).
7. Placement rules: the template's caption, tooltip and icon show first; after `setLabel()`
   every placement shows the new label (what `setItemHtmlById` does today). A placement shows
   only if its own `visible` and the action's are both true.
8. Pattern for P3-10…P3-13: register `new CommandAction(ActionId.NEW_PROJECT,
   MESSAGES.newProjectButton(), IconKey.ADD, new NewProjectAction())` in
   `Ode.registerActions()`. Templates not yet migrated keep nesting their own `Command`
   instance, which runs the same code. A class that a ticket must rewrite anyway becomes an
   `Action` subclass in `core/actions/<area>/` (decision 0005). Dynamic lists (screens,
   languages) stay `Command` items built in code.

## Acceptance criteria
- [ ] `core/actions` imports nothing from `com.google.gwt`, controls, features or layouts
      (`CommandAction` lives in `actions/` because it holds a GWT `Command`).
- [ ] `ActionRegistryTest`: missing id fails, duplicate id fails, listeners fire once per change.
- [ ] A scratch item with `action="…"` builds and runs its action (checked locally, not committed).
- [ ] No `.ui.xml` file changes; every template compiles as before.
- [ ] Snapshot diff shows no change in classic or neo, light or dark.

## Rules
- At most ~400 added lines and ~20 files; one line per id in `ActionId`, no per-id Javadoc.
- No visual change.
- `Command` children keep working until P3-14.

  no AI attribution.
