## Summary
A new `controls/` package defines the contracts for buttons, toolbars, menus and icons, plus a
`StandardControls` that implements them by wrapping today's widgets, and a `SharedView` base class
whose `@UiFactory` methods hand UiBinder the active layout's controls. Menu keyboard handling is
pulled out of `DropDownButton` into `controls/behaviour/MenuKeyboard`. No template changes yet;
users see no change.

## Why
- Every layout draws its buttons and menus with the same concrete classes:
  `widgets/TextButton.java` (85 lines, extends `PushButton`), `widgets/DropDownButton.java`
  (602 lines), `widgets/Toolbar.java` (313), `widgets/ContextMenu.java` (326, a `final` class
  around a `PopupPanel` and `MenuBar`). Neo differs from classic only by CSS and an `icon=`
  attribute, so a layout cannot change markup without changing everyone's.
- `DropDownButton`'s constructor (lines 124-250) holds all the menu keyboard logic and
  registers three global `Event.addNativePreviewHandler`s per instance (lines 179, 221, 234:
  Home/End/type-ahead, Tab, Escape) that are never removed.
- Custom parsing comes from `@ElementParserToUse` (patched UiBinder shipped in
  `lib/gwt_svg/lib-gwt-svg-0.5.15.jar`); `TextButtonParser` only fires when
  `type.getName().equals("TextButton")` (TextButtonParser.java:20).
- Two different `Icon` classes exist. `components/Icon.java` (an `InlineLabel` with the
  `material-icons` class) is the toolbar icon; `widgets/Icon.java` is an image-plus-caption
  used only by `editor/simple/components/MockNonVisibleComponent.java` and is not a control.

## Steps
1. Write the contracts. Every visual piece extends `IsWidget`. Setters that templates use
   as attributes (`setText`, `setAction(ActionId)`, `setIcon(IconKey)`, `setAlign`,
   `setEnabled`) are declared on the interface, because UiBinder calls setters on the
   declared type. `Controls` has one factory per piece: `button()`, `iconButton()`,
   `menuButton()`, `menuItem()`, `toolbar()`, `toolbarItem()`, `contextMenu()`, `icon()`.
2. `Controls.java` (the factory interface): `static Controls active()` and
   `static void install(Controls)`; defaults to `StandardControls`.
3. `SharedView.java`: `public abstract class SharedView extends Composite` with one `@UiFactory`
   per controls type that returns `Controls.active().button()` and so on (`docs/06-controls.md`). UiBinder
   finds `@UiFactory` methods on superclasses, so subclasses need nothing else.
4. `MenuKeyboard`: one class that attaches to a trigger element and a menu, handles
   Up/Down/Home/End/type-ahead/Tab/Escape, keeps `aria-expanded` in step, and registers its
   native preview handler on open and removes it on close. Keep the type-ahead index math
   in a pure static method so `MenuKeyboardTest` can run as a plain JUnit test.
5. Make `DropDownButton` and `ContextMenu` delegate to `MenuKeyboard`; delete the inline
   handlers.
6. `StandardButton extends TextButton implements Button` (same DOM, same
   `ode-TextButton` class), `StandardMenuButton extends DropDownButton implements
   MenuButton`, `StandardToolbar extends widgets.Toolbar implements Toolbar`,
   `StandardIcon extends components.Icon implements Icon`. `StandardContextMenu` composes
   `widgets.ContextMenu` (it is `final`).
7. `ActionBinding.bind(control, ActionId)`: looks the action up in `ActionRegistry`, runs
   it on click, and calls the control's `render(Action)` on every change. Every standard
   control's `setAction` uses it.
8. Put `@ElementParserToUse(className = "...controls.uibinder.ActionItemParser")` on the
   `MenuButton` and `Toolbar` interfaces; UiBinder's breadth-first hierarchy walk
   (`UiBinderWriter.getParsersForClass`) finds it on interfaces. The parser turns child
   `<c:Item action="…"/>` elements into `addItem(…)` calls. A concrete element such as
   `<c:NeoMenuButton>` (P5-26) also inherits `DropDownButtonParser` from its superclass,
   so make the old parsers skip types that implement the control interface.

## Acceptance criteria
- [ ] `controls/` contains the nine contracts, `Controls`, `SharedView`, and `controls/standard/` the seven
      standard classes; nothing in `controls/` imports `layouts/` or `features/`.
- [ ] A `StandardButton` bound with `setAction(NEW_PROJECT)` follows the action's label,
      enabled and visible state.
- [ ] `DropDownButton` registers no global preview handler in its constructor; open,
      arrow keys, Home/End, type-ahead, Tab and Escape behave as before in every menu.
- [ ] Opening and closing a menu 20 times leaves no extra native preview handlers.
- [ ] `MenuKeyboardTest` passes under `ant tests`.
- [ ] No `.ui.xml` changes; snapshot diff shows no change in classic or neo, light or dark.

## Rules
- At most ~400 added lines and ~20 files. If it runs over, land steps 4-5 (MenuKeyboard)
  as the first PR and the contracts plus `StandardControls` as the second.
- No visual change.
- Old widgets keep working; the views keep using them until P5-26.
- Short conventional commit subjects, e.g. `refactor(controls): button and menu contracts`;
  no AI attribution.

## How to verify
- `ant -Dskip.ios=true noplay`, `ant tests`, `ant BlocklyTest`
- Snapshot screens (P0-02), classic/neo × light/dark.
- By hand, in both layouts: open the Projects menu with the mouse and with Enter; use
  Up/Down, Home/End, type "S" twice, Tab and Escape; focus returns to the button.
