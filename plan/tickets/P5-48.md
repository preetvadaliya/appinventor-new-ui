## Summary
Reordering a component in the component tree uses the same drag engine as the viewer (P5-47)
instead of the browser's HTML5 drag and drop written inline. Each tree row is a `Draggable`
(payload `COMPONENTS`), the tree is a `DropTarget` with zone `TREE`, a drop runs
`MoveComponents` and asks `ComponentRules` (P3-45), and the tree's hint is styled by the
layout's CSS. Classic and neo look as before; Escape cancels this drag too.

## Why
- The tree is the one designer drag still on a second mechanism: HTML5 drag and drop in
  `explorer/SourceStructureExplorer.java:208` onward, with its own hint drawn in three zones
  per row (before, into, after; lines 82-90), its own acceptance test
  (`MockContainer.willAcceptComponentType`) and no way for a layout to change it.
- Keeping it would save 1.5 days but leave two hint styles and two code paths for the same
  move (decision 0015).

## In scope
- `ComponentTreePresenter.View` (from P5-32) reports a drag of the selected nodes and a drop at
  a node and a zone (before, into, after); the presenter asks `ComponentRules.canContain` and
  runs `MoveComponents`. Dropping on a node that cannot hold the child is refused, as today.
- `ClassicComponentTree` and `NeoComponentTree` (and their tree control): rows become
  `Draggable`s, the tree registers as a `DropTarget` (`zone()` returns `DropZone.TREE`);
  `onHover` shows the line or box for the pointer's zone using a layout CSS class, and
  `onLeave` clears it. The tree's own `ondragstart`, `ondragover` and `ondrop` handlers are gone.
- Multi-selection: dragging a selected node drags the whole selection, as today.
- The tree hint's CSS moves to each layout's `views/editor.css`, with the colour from
  `--color-drop-hint` (P5-47).
- The keyboard path (Alt+Up/Down) already runs `MoveComponents` (P3-45); check it still does.

## Out of scope
- Dragging from the tree into the viewer; the tree stays a source and a target of its own
  reorders only.
- The preview for a tree drag in nova (a later ticket); classic and neo show the node's row.
- Blocks drawers (P5-43).

## Steps
1. Make the tree's rows `Draggable` and the tree a `DropTarget` in both layouts, with the zone
   computed from the pointer's position inside a row (`DropPoint`).
2. Move the hint into CSS classes in each layout's `editor.css`; delete the inline drawing and
   the HTML5 handlers from `SourceStructureExplorer` (or from the new tree view if P5-32 has
   already replaced it).
3. Add the presenter test: a drop before, into and after a node, an illegal drop, and a
   selection of two.

## Acceptance criteria
- [ ] No HTML5 drag event (`dragstart`, `dragover`, `drop`) is used in the component tree.
- [ ] Dragging a node before, into and after another reorders as before; a refused drop shows
      no hint and changes nothing; Escape cancels.
- [ ] The presenter's tests pass under `ant tests`; `core/` imports no widget.
- [ ] Snapshot diff shows no change in classic or neo, light or dark.

## Rules
- At most ~400 added lines and ~20 files.
- No visual change beyond Escape. A layout never imports another layout.
- Short conventional commit subjects, e.g. `refactor(designer): tree drops run on the drag
  engine`; no AI attribution.
