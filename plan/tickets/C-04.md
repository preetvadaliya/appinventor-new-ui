## Summary
Decide whether a property editor shows a wrong value (a letter in FontSize, 120 percent
in Width) as an inline error under the field, or keeps today's browser `Window.alert`.
Record the answer in `docs/decisions/0012-editor-errors.md` before P5-30 starts, and
make the examples and P5-30/P5-31 match it. No code changes.

## Why
- Today every editor that checks its value calls `Window.alert`: for example
  `YoungAndroidLengthPropertyEditor` (`MESSAGES.nonnumericInputError()`,
  `MESSAGES.nonvalidPercentValue()`) and the number editors in `widgets/properties/`.
- The examples already route errors through the view (`NumberEditorModel.View.showError`,
  `LengthEditorModel.View.showError`), so either answer works without changing a model.
- An inline error is a visible change, and P5 promises none, so this needs a decision
  instead of being slipped into a refactor PR.

## In scope
- Two options, with a recommendation, posted on this issue:
  1. Keep `Window.alert` in P5 (the view's `showError` calls it); move to inline errors
     later in a ticket that is allowed to change the look.
  2. Inline errors from the start (`TextField.setError`, a `properties-Error` label), as an
     agreed exception to "no visual change", with MIT's OK in the umbrella issue (C-01).
- `docs/decisions/0012-editor-errors.md`
- Matching edits to P5-30, P5-31 and the two example models' comments

## Out of scope
- Errors in dialogs and wizards (they keep what they show today)
- Any code in `appinventor-sources`
